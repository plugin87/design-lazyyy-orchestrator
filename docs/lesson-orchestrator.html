ศูนย์บัญชาการ Orchestrator คืออะไร

มันคือ ห้องทำงานจำลอง ที่มีทีม agent 11 ตำแหน่งนั่งอยู่ คุณเป็นคนตั้งโจทย์ แล้วดูพวกเขาทำงานให้ตั้งแต่เก็บความต้องการ ออกแบบ เขียนโค้ด ตรวจคุณภาพ จนถึงปล่อยของ

แต่สิ่งที่ต้องเอากลับบ้านจากบทเรียนนี้ ไม่ใช่เอกสารสวย ๆ ที่ได้มา คือคำตอบของคำถามเดียว

ระบบนี้รู้ได้ยังไงว่างานที่ทำออกมาใช้ได้

ทุกอย่างในหน้านี้มีไว้เพื่อให้คุณตอบคำถามนั้นได้ด้วยตัวเอง

ก่อนเริ่ม ต้องมีอะไรบ้าง

  • Claude Code ติดตั้งแล้วและล็อกอินแล้ว
  • Node.js รุ่น 18 ขึ้นไป (พิมพ์ node -v เช็กได้)
  • Python 3 (พิมพ์ python3 --version เช็กได้)
  • Git

ไม่ต้อง npm install อะไรเลย ตัวห้องบัญชาการเขียนด้วยของที่ Node มีมาให้อยู่แล้ว

ขั้นที่ 1 · ดาวน์โหลดโปรเจกต์

git clone https://github.com/plugin87/design-lazyyy-orchestrator.git
cd design-lazyyy-orchestrator

หรือกดปุ่ม Code → Download ZIP ที่หน้า GitHub แล้วแตกไฟล์ก็ได้

เปิดหน้าโปรเจกต์บน GitHub

ขั้นที่ 2 · เปิดห้องบัญชาการ

node tools/monitor/server.mjs --allow-run

แล้วเปิดเบราว์เซอร์ไปที่ http://localhost:4173

ทำไมต้องมี --allow-run เพราะถ้าไม่ใส่ ปุ่มสั่งงานบนหน้าเว็บจะถูกปิดไว้ หน้าเว็บจะเปิดดูได้ แต่สั่งอะไรไม่ได้ นี่คือค่าเริ่มต้นที่ตั้งใจให้ปลอดภัย

หน้าแรกมีสามอย่าง

  • โฟลเดอร์เก็บงาน — กด "เลือกโฟลเดอร์…" ถ้าอยากเปลี่ยนที่เก็บ
  • รายการโปรเจกต์ ที่เคยเปิดไว้ พร้อมจุดหกจุด คือด่านตรวจ G1 ถึง G6
  • ปุ่มเปิดโปรเจกต์ใหม่

ขั้นที่ 3 · เปิดโปรเจกต์ของตัวเอง

กด + เปิดโปรเจกต์ใหม่ แล้วกรอกหกช่อง

  • ชื่อโครงการ — ชื่อที่คุณจะเรียกมันจริง ๆ
  • รหัสสามตัวอักษร — ใช้แทนรหัสเอกสารทุกฉบับ เช่น PRD-ABC-001 เลือกแล้วเปลี่ยนยาก คิดให้ดีก่อน
  • ปัญหาในหนึ่งประโยค — เขียนเป็น ปัญหา ไม่ใช่ วิธีแก้
  • ใครเจอปัญหานี้ — เจาะจงกว่าคำว่า "ผู้ใช้"
  • วันนี้เขาทำยังไง — ถ้ายังไม่มีของคุณ เขาแก้ปัญหาด้วยอะไรอยู่
  • มีเวลากี่วัน — ถ้าไม่รู้ ปล่อยว่างไว้

ตัวอย่างที่ถูกกับที่ผิด

  • ถูก — "นักเรียนลืมว่ามีการบ้านอะไรต้องส่งบ้าง"
  • ผิด — "อยากได้แอปจดการบ้าน" อันนี้เป็นวิธีแก้ ไม่ใช่ปัญหา

สังเกตให้ดี ช่องที่คุณเว้นว่างจะกลายเป็น TBD — ต้องการ [คน/ข้อมูล] แล้วขึ้นเป็นคำถามค้างไว้ ระบบจะไม่เดาแทนคุณ

เปิดไฟล์ project/project.yml ดูด้วยตาตัวเอง ว่ามันเป็นอย่างนั้นจริง

ขั้นที่ 4 · สั่งสายงานทำงาน แล้วดู

กดปุ่ม ▶ สั่งสายงานทำงาน แล้วห้องจะเริ่มขยับ

อ่านห้องให้ออก ว่าแต่ละอย่างบอกอะไร

  • ตัวละครสว่าง — บทบาทนั้นกำลังทำงานอยู่จริง ไม่ใช่แอนิเมชันประดับ
  • ชื่อไฟล์บนการ์ด — ไฟล์ที่มันเพิ่งเขียนลงดิสก์จริง ๆ
  • ระยะ 3/7 มุมขวาบน — ระยะที่เท่าไรจากเจ็ด ไม่ใช่ เปอร์เซ็นต์ที่เดาว่างานเสร็จไปเท่าไร
  • tokens และเทิร์น — ค่าใช้จ่ายจริงของการรันครั้งนี้
  • ป้าย G1 ถึง G6 — ด่านที่ผ่านแล้ว ป้ายว่าง = ยังไม่ผ่าน ไม่ใช่ยังไม่ได้ตรวจ

ระหว่างรอ ให้เปิดโฟลเดอร์โปรเจกต์ทิ้งไว้ แล้วดูไฟล์เกิดขึ้นจริง ๆ สิ่งที่อยู่บนจอกับสิ่งที่อยู่ในดิสก์ต้องตรงกัน ถ้าไม่ตรง แปลว่าจอโกหก

ขั้นที่ 5 · อ่านคำตัดสิน

พอจบ ตัวตรวจที่ชื่อ correcter จะให้คำตัดสินหนึ่งในสามอย่าง

  • PASS — ตรวจกับของจริงแล้วผ่าน ไปด่านถัดไปได้
  • CORRECTED — มีข้อบกพร่องที่แก้ได้เอง แก้แล้วสั่งตรวจใหม่
  • BLOCKED — ต้องใช้คนจริงหรือข้อมูลจากโลกจริง ให้หยุด แล้วไปหาคนหรือหาข้อมูลมา

สั่งตรวจเองเมื่อไรก็ได้

python3 tools/correcter/verify.py

BLOCKED ไม่ใช่ความล้มเหลว และห้ามหาทางอ้อม

ห้ามเติมตัวเลขที่ไม่รู้เพื่อให้ผ่าน ห้ามปิดตัวตรวจ ห้ามลดเกณฑ์

สายงานที่ผ่านได้เสมอ คือสายงานที่ไม่ได้พิสูจน์อะไรเลย

ทีมงาน 11 ตำแหน่งในห้อง

  • Project Intake — รับโจทย์ ทำ project.yml
  • Product Owner — PRD ความต้องการ
  • Project Manager — ประมาณการ แผนงาน ตาราง
  • Systems Analyst — SRS สถาปัตยกรรม โครงข้อมูล แผนทดสอบ
  • UX/UI Designer — งานออกแบบและ design token
  • Frontend Developer — โค้ดฝั่งหน้าจอ
  • Backend Developer — โค้ดฝั่งเซิร์ฟเวอร์
  • Lead Reviewer — ตรวจโค้ด
  • QA — ตรวจคุณภาพ
  • DevOps / Release — ปล่อยของ
  • Document Control — ทะเบียนเอกสาร ทำทุกระยะ

คำสั่งที่ใช้บ่อย

พิมพ์ในช่องแชทมุมขวาล่างของห้องได้เลย คุยต่อเนื่องและถามกลับได้

  • /kickoff — เปิดโปรเจกต์ด้วยการสัมภาษณ์ แทนการกรอกฟอร์ม
  • /status — ตอนนี้โปรเจกต์อยู่ตรงไหน อะไรยังเป็น TBD
  • /gate — ตรวจว่าขาดอะไรก่อนไปด่านถัดไป
  • /doc-new <TYPE> — สร้างเอกสารพร้อมลงทะเบียนในครั้งเดียว
  • /cr — เจอข้อขัดแย้ง ให้ออกคำขอเปลี่ยนแปลง ไม่ใช่แก้เงียบ ๆ
  • /monitor — เปิดห้องบัญชาการ

กติกาสี่ข้อที่อยู่เหนือทุกอย่าง

1 · ไม่รู้ห้ามเดา

ข้อกำหนดที่แต่งขึ้นแย่กว่าช่องว่าง เพราะช่องว่างมีคนเห็นแล้วมาเติม แต่ของที่แต่งขึ้นมองไม่เห็น แล้วถูกสร้างต่อไปเรื่อย ๆ

2 · ด่านที่ผ่านตลอดไม่ใช่ด่าน

ถ้าหาหลักฐานไม่เจอ แปลว่ายังไม่ผ่าน ไม่ใช่ผ่าน

3 · เจอขัดแย้งให้รายงาน อย่าแก้เงียบ

เจอข้อกำหนดตีกัน ให้ออก /cr ไม่ใช่เลือกข้างแล้วสร้างต่อ

4 · คนตรวจไม่แก้ของ

code-reviewer กับ quality-assurance ถูกตัดสิทธิ์แก้ไฟล์ ในระดับเครื่องมือ ไม่ใช่แค่ขอความร่วมมือ

เปิด .claude/agents/code-reviewer.md ดูบรรทัด tools: จะเห็นว่าไม่มี Write กับ Edit อยู่จริง ๆ

ใบงาน · ห้าอย่างที่ต้องหาให้เจอ

ทำระหว่างที่ระบบกำลังเดิน ไม่ต้องรอให้จบ

  1. เปิด project/project.yml — มี TBD กี่จุด และแต่ละจุดต้องใช้ ใคร มาตอบ
  2. เปิด PRD ที่ได้ — เลือกข้อกำหนดมาหนึ่งข้อ แล้วไล่ว่ามันไปโผล่ที่ไหนบ้างใน SRS ถ้าไล่ไม่เจอ แปลว่าตารางตรวจย้อนกลับขาด นั่นคือข้อบกพร่องที่ต้องรายงาน
  3. เปิด tools/correcter/checks.py — เลือกตัวตรวจมาหนึ่งตัว อ่านว่ามันวัดอะไรจากไฟล์จริง แล้วตอบว่า ถ้าตัวตรวจนั้นหาไฟล์ไม่เจอ มันจะตกหรือจะเงียบ
  4. ลองทำให้ด่านตก — แก้เอกสารให้ขัดกันเอง แล้วรัน verify.py ถ้ามันยังผ่าน แปลว่าด่านนั้นวัดไม่จริง เขียนรายงานว่าด่านไหนและเพราะอะไร
  5. ดูที่ open_questions — เลือกมาหนึ่งข้อ แล้วเขียนว่าจะได้คำตอบมาจากใคร ด้วยวิธีอะไร ใช้เวลาเท่าไร

ข้อ 3 สำคัญที่สุดในใบงานนี้

ตอนสร้างระบบนี้เจอของจริงว่า ตัวตรวจหลายตัวเคย ฝังรหัสโครงการไว้ในตัวอักษร พอชี้ไปโปรเจกต์อื่น มันหาเอกสารไม่เจอ คืนรายการว่าง แล้วรายงานว่าผ่านเหมือนเดิม

ประตูที่เงียบเพราะหาของไม่เจอ อันตรายกว่าประตูที่ตก เพราะประตูที่ตกมีคนไปดู ส่วนประตูที่เงียบไม่มีใครรู้ว่ามันเลิกทำงานไปแล้ว

ถ้าห้องไม่ขยับ

  1. รัน python3 tools/monitor/emit.py --selftest ดูว่าตัวรับเหตุการณ์ยังดีอยู่ไหม
  2. รัน cat .monitor/events.jsonl ดูว่า hook ส่งถึงหรือเปล่า
  3. Claude Code อ่าน hooks ตอนเปิด session เท่านั้น ถ้าคุณเปิด session ค้างไว้ตั้งแต่ก่อนแก้ .claude/settings.json มันจะไม่ส่งอะไรเลย ปิดแล้วเปิดใหม่

ถ้ายังไม่ขยับ ให้เช็กว่าเปิดเซิร์ฟเวอร์ด้วย --allow-run หรือเปล่า
